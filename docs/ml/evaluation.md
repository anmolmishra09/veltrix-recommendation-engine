# Evaluation

## Overview

Evaluation is crucial for measuring the effectiveness of the recommendation system and guiding improvements. We evaluate both the candidate generation and ranking stages, as well as the overall system performance.

## Evaluation Framework

We use a combination of offline and online evaluation methods to ensure that our models perform well in both controlled experiments and real-world conditions.

### Offline Evaluation
- Conducted on historical data before deploying models to production.
- Allows for rapid experimentation and comparison of different algorithms.
- Prone to biases due to the nature of logged data (e.g., position bias, selection bias).

### Online Evaluation
- Conducted in production with real users (typically via A/B tests).
- Provides the most accurate measure of true user impact.
- Slower and more expensive than offline evaluation but essential for final validation.

## Key Metrics

### Candidate Generation Metrics

#### Recall@K
- **Definition**: The proportion of actual user interactions (e.g., clicks, purchases) that appear in the top-K candidates generated by the candidate generator.
- **Formula**: Recall@K = (Number of relevant items in top-K) / (Total number of relevant items for the user)
- **Interpretation**: Higher recall means the candidate generator is better at capturing relevant items.
- **Typical Values**: For a good candidate generator, Recall@100 should be >0.6 for e-commerce data.

#### Mean Reciprocal Rank (MRR)
- **Definition**: The average of the reciprocal ranks of the first relevant item in the candidate list.
- **Formula**: MRR = (1 / |U|) * Σ_{u∈U} (1 / rank_u)
  where rank_u is the position of the first relevant item for user u, and |U| is the number of users.
- **Interpretation**: Higher MRR means relevant items appear higher in the candidate list on average.

#### Coverage
- **Definition**: The percentage of the item catalog that is recommended to users over a period.
- **Formula**: Coverage = (Number of unique items recommended) / (Total number of items in catalog) * 100%
- **Interpretation**: Higher coverage means the system is not overly concentrated on a few popular items.

### Ranking Metrics

#### Precision@K
- **Definition**: The proportion of recommended items in the top-K that are relevant (e.g., clicked or purchased).
- **Formula**: Precision@K = (Number of relevant items in top-K) / K
- **Interpretation**: Higher precision means the ranking model is better at ordering relevant items higher.

#### Normalized Discounted Gain (NDCG@K)
- **Definition**: Measures the usefulness of items based on their position in the recommendation list. Higher positions are weighted more heavily.
- **Formula**: 
  DCG@K = Σ_{i=1}^K (rel_i / log2(i + 1))
  NDCG@K = DCG@K / IDCG@K
  where rel_i is the graded relevance of the item at position i, and IDCG@K is the ideal DCG@K.
- **Interpretation**: Higher NDCG means the ranking model is better at placing relevant items at the top of the list.

#### Mean Average Precision (MAP)
- **Definition**: The average of the average precision scores for each user.
- **Formula**: 
  AP_u = (1 / num_relevant_u) * Σ_{k=1}^N (P_u(k) * rel_u(k))
  MAP = (1 / |U|) * Σ_{u∈U} AP_u
  where P_u(k) is the precision at cut-off k for user u, and rel_u(k) is 1 if the item at position k is relevant for user u, else 0.
- **Interpretation**: Higher MAP means the ranking model is better at ranking relevant items higher across the entire list.

### Business Metrics

#### Click-Through Rate (CTR)
- **Definition**: The percentage of recommendation impressions that result in a click.
- **Formula**: CTR = (Number of clicks) / (Number of impressions) * 100%
- **Interpretation**: Higher CTR indicates that recommendations are more engaging to users.

#### Conversion Rate
- **Definition**: The percentage of recommendation impressions that result in a purchase.
- **Formula**: Conversion Rate = (Number of purchases) / (Number of impressions) * 100%
- **Interpretation**: Higher conversion rate indicates that recommendations are more effective at driving sales.

#### Revenue per Recommendation (RPR)
- **Definition**: The average revenue generated from a recommendation impression.
- **Formula**: RPR = (Total revenue from recommendations) / (Number of impressions)
- **Interpretation**: Higher RPR indicates that recommendations are more profitable.

#### Diversity
- **Definition**: A measure of how varied the recommended items are (e.g., across categories, brands, or price points).
- **Common Metrics**:
  - **Category Coverage**: Percentage of unique categories recommended.
  - **Entropy**: Measures the uncertainty in the distribution of recommended items across categories.
  - **Gini Index**: Measures inequality in the distribution of recommendations (lower means more even distribution).
- **Interpretation**: Higher diversity means users are exposed to a wider range of items, which can increase long-term engagement.

## Evaluation Process

### Offline Evaluation Pipeline

1. **Data Preparation**
   - Split historical data into training, validation, and test sets (e.g., 70%/10%/20% by time).
   - Ensure that the test set contains future interactions relative to the training set to avoid data leakage.

2. **Feature Generation**
   - Compute features for the training, validation, and test sets using the same feature pipelines used in production.
   - Store features in the feature store's offline store for consistency.

3. **Model Training**
   - Train models on the training set.
   - Tune hyperparameters using the validation set.
   - Log models and metrics to MLflow.

4. **Offline Inference**
   - Generate recommendations for users in the test set using the trained models.
   - For each user, retrieve the actual interactions in the test set as ground truth.

5. **Metric Calculation**
   - Compute candidate generation metrics (Recall@K, MRR) using the candidate generators.
   - Compute ranking metrics (Precision@K, NDCG@K, MAP) using the ranked recommendations.
   - Compute business metrics (CTR, conversion rate, RPR) if revenue or conversion data is available in the test set.

6. **Analysis**
   - Compare metrics across different models and configurations.
   - Perform statistical significance testing (e.g., t-test, bootstrap) to confirm improvements.
   - Analyze performance across user segments (e.g., new vs. returning users, heavy vs. light users).

### Online Evaluation (A/B Testing)

1. **Experiment Design**
   - Define the control (current production model) and treatment (new model) groups.
   - Determine the allocation ratio (e.g., 50% control, 50% treatment).
   - Set the minimum detectable effect and required sample size.

2. **Implementation**
   - Route incoming requests to either the control or treatment group based on a hash of the user ID or session ID.
   - Ensure that all other factors (e.g., features, filtering rules) are identical between groups.

3. **Data Collection**
   - Log impressions, clicks, purchases, and revenue for each recommendation.
   - Track user-level metrics to avoid double-counting.

4. **Analysis**
   - Compute metrics (CTR, conversion rate, RPR) for each group.
   - Calculate the lift (relative improvement) of the treatment group over the control group.
   - Perform statistical tests (e.g., chi-squared test for proportions) to determine significance.
   - Monitor for any negative impacts on user experience (e.g., increase in error rates).

5. **Decision**
   - If the treatment shows a statistically significant improvement in the primary metric (e.g., CTR) with no negative secondary effects, promote the treatment to control.
   - Otherwise, keep the control and iterate on the treatment.

## Implementation Details

### Evaluation Scripts
- `ml/evaluate.py`: Main script for offline evaluation.
- `ml/compare_models.py`: Script to compare multiple models from MLflow.
- `ml/ab_test_analyzer.py`: Script to analyze A/B test results.

### Logging and Tracking
- All experiments are logged to MLflow with parameters, metrics, and artifacts.
- Model versions are registered in the MLflow Model Registry.
- Evaluation scripts generate plots (e.g., precision-recall curves, ROC curves) and save them as artifacts.

### Data Requirements
- For offline evaluation, we need:
  - User features (historical interactions up to a cutoff time).
  - Item features (static attributes and historical interactions up to a cutoff time).
  - Ground truth interactions in the test period.
- For online evaluation, we need:
  - Instrumentation to log impressions and interactions.
  - A system to assign users to experimental groups consistently.

## Challenges and Solutions

### Popularity Bias
- **Problem**: Offline evaluation can favor popular items because they appear more frequently in the training data.
- **Solutions**:
  1. Use stratified sampling to ensure adequate representation of niche items.
  2. Normalize metrics by item popularity to get a fairer comparison.
  3. Focus on metrics that are less biased (e.g., MRR, which rewards ranking relevant items high).

### Position Bias
- **Problem**: In logged data, users are more likely to interact with items that appear in higher positions, regardless of relevance.
- **Solutions**:
  1. Use inverse propensity scoring (IPS) to weight observations by the inverse of the probability of exposure.
  2. Compare algorithms using the same logging policy (e.g., always expose items in random order during evaluation).
  3. Use interleaving experiments online to compare algorithms without being affected by position bias.

### Cold Start
- **Problem**: Offline evaluation often excludes users and items with insufficient history, biasing results toward active users and popular items.
- **Solutions**:
  1. Explicitly measure performance on cold-start users (those with zero or few interactions in the training set).
  2. Use hybrid approaches that combine collaborative filtering with content-based methods.
  3. Report metrics separately for different user cohorts (e.g., new, returning, power users).

## Best Practices

### 1. Evaluate What Matters
- Align metrics with business goals (e.g., if the goal is to increase revenue, prioritize RPR and conversion rate).
- Don't optimize for metrics that don't correlate with user satisfaction or business outcomes.

### 2. Use Long-Term Metrics When Possible
- Short-term metrics like CTR can be gamed (e.g., by using clickbait).
- Long-term metrics like retention, lifetime value, and return visits are harder to manipulate but more meaningful.

### 3. Account for Uncertainty
- Always report confidence intervals or p-values when comparing metrics.
- Avoid making decisions based on small or statistically insignificant differences.

### 4. Evaluate End-to-End
- While component-level evaluation (e.g., just the ranking model) is useful, ensure that the entire pipeline works well together.
- Evaluate the system as a whole in A/B tests whenever possible.

### 5. Reproducibility
- Use fixed random seeds for offline experiments.
- Log all dependencies, data versions, and hyperparameters.
- Store evaluation scripts and data splits in version control.
